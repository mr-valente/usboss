# Fix out-of-order input reports and bound the write path

Every USB input report spawned its own coroutine on Dispatchers.IO, eachcontending for a shared writer mutex before doing a blocking socket write. Two defects follow from that. First, coroutines dispatched across the IOpool reach the mutex in nondeterministic order, so reports could be writtenout of order -- a stale full-state XInput snapshot landing after a newer oneshows up as a stick snapping back or a button sticking for a frame. Thisneeds no network problem to fire; it happens whenever two reports overlap,which a GC pause or scheduler preemption is enough to cause.

Second, the queue was unbounded and dropped nothing, so a stalled socketbuilt a backlog of stale controller state that was replayed in full oncethe write unblocked.

Replace both with a single SessionWriter per session: one coroutine owns the output stream, so frames cannot be reordered- control frames queue losslessly and drain first, so a reply cannot  overtake the HELLO_ACK or OPEN_DEVICE_ACK before it- input reports go to a conflating slot keyed by report id, so at most one  report per id is ever pending

Report handoff stays non-blocking, which was the point of the originalcomment on the USB read path. On a healthy link the conflating slot neverfires; the superseded counter logs when it does.

Also on the Linux client:
- write the 20 events of an XInput report in one uinput write instead of 20
- buffer socket reads, halving the syscalls per frame
